Releases

libraries and apps

01

Two Release Types

What a repo makes decides how it ships.

LIBRARIES GitHub Actions → Publish

A versioned artifact goes to Nexus. The version is the name — other code depends on exactly it.

DELIVERABLES Git Tag → Deploy

Make a release branch, put a tag on it — that tag is the release. The CCoE then deploys it to AWS.

02

Who Depends on the Version

The split is on purpose. It comes down to who depends on the version number.

A library is its version

Immutable: Nexus never overwrites a published version, and the build is reproducible. Other code pins exactly this — forever.

A deliverable is a tagged commit

The version, the tag, and the commit are the same thing — the release. Nothing builds against it; it just marks which commit went live.

The Dance

Re-design this from scratch and you'd land on exactly this flow — then watch how much of it is done by hand.

04

Can we delete the dance?

Can we drop the manual version bumps — and let the git tag carry it?

Today

Let git set the version

The pom keeps a dummy version forever. Every push makes a snapshot for free.

A release becomes just a git tag.
No version PRs.

addendum

Options

The architecture stays exactly as it is — it's how we want it. We only automate the mechanical part: the by-hand version bumps. Two off-the-shelf ways:

CI-friendly versions

plain maven · minimal change

<!-- pom.xml: version is a placeholder --> <version>${revision}</version> <properties> <revision>1.3.0-SNAPSHOT</revision> <!-- one place --> </properties> # release: pass the number, no PR mvn deploy -Drevision=1.3.0

The version lives in one property, not scattered through the pom. To release, the build passes the number on the command line — instead of a PR that edits the pom. (flatten-maven-plugin writes the real number into what Nexus receives.)

git-versioning extension

qoomon · most automatic

<!-- .mvn/extensions.xml --> <extension> <groupId>me.qoomon</groupId> <artifactId>maven-git-versioning-extension</artifactId> <version>9.12.0</version> </extension> <!-- .mvn/…-extension.xml --> <ref type="tag"> <pattern>v(?<version>.*)</pattern> <version>${ref.version}</version> </ref>

The pom holds a placeholder, untouched. Tag v1.3.0 → ships 1.3.0; nothing edited by hand. The branch SNAPSHOT name is derived from git.

Also: jgitver derives the version from the last tag plus commit distance — even less config, but more opinionated (less flexible).
